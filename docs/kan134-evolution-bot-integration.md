# KAN-134: Evolution QA and application integration

## Scope

- Evolution 2.3.7: `https://evolution-staging.clicaepede.com.br`.
- Application remains on Vercel. Production infrastructure migration is out of scope.
- Pilot store: Ccocobongo (9). Other stores are excluded by rollout configuration.
- No LLM credentials or intelligence evaluation. Use fixed transactional messages.
- Pairing requires the owner's explicit authorization and WhatsApp Linked Devices.
- Do not commit telephone numbers, QR images, instance tokens, API keys or webhook secrets.

## Configuration

Server-only Vercel variables:

| Variable | Purpose |
| --- | --- |
| `WHATSAPP_EVOLUTION_API_BASE_URL` | QA provider HTTPS endpoint |
| `WHATSAPP_EVOLUTION_API_KEY` | Provider authentication |
| `WHATSAPP_EVOLUTION_WEBHOOK_SECRET` | Shared Bearer credential on callbacks |
| `IFOOD_TOKEN_ENCRYPTION_KEY` | Existing AES-GCM application encryption key for instance tokens |
| `WHATSAPP_BOT_ROLLOUT_MODE` | `pilot` |
| `WHATSAPP_BOT_PILOT_STORE_IDS` | `9` |

Production and the KAN-134 branch preview are configured separately. Environment
changes require a new deployment before taking effect. Never rotate an existing
encryption key without migrating ciphertext. Temporary local copies are protected
with Windows DPAPI and a restricted ACL outside the repository.

The instance name is generated by the app from store and number record IDs. The
webhook uses `/api/webhooks/whatsapp/evolution`, with only `CONNECTION_UPDATE`,
`QRCODE_UPDATED`, and `MESSAGES_UPSERT`. `byEvents:false` is required: otherwise
Evolution appends an event-specific URL path that does not exist in the app.
`base64:false` avoids inline message media; QR events still contain the pairing QR.
See the [version-pinned provider implementation](https://github.com/evolution-foundation/evolution-api/blob/2.3.7/src/api/integrations/event/webhook/webhook.controller.ts).

## Database reconciliation

The live project did not contain the eight KAN-81 WhatsApp tables. Do not push all
historical migrations or mark historical migrations applied without verification.
The KAN-134 migration reconciles this domain explicitly, checks schema prerequisites,
keeps tenant-scoped foreign keys and deduplication indexes, forces RLS and revokes
public/anon/authenticated privileges. It extends the deployed audit action predicate
without removing existing administrative actions. This does not resolve unrelated
historical migration drift.

## Acceptance matrix

| Case | Required evidence |
| --- | --- |
| QA instance | Instance exists with only the approved settings |
| Pairing | Owner scans QR; provider and app report connected |
| Environment separation | Server-only variables, instance identifier and webhook target verified |
| Webhook | Real provider callback reaches the deployed app |
| Event allowlist | Exact three events configured; unrelated events ignored |
| Authentication | Wrong/missing credential rejected; valid callback accepted |
| Real inbound | A different phone sends a unique QA marker; exactly one DB message |
| Real outbound | App transactional queue sends a fixed message; recipient confirms receipt |
| Reconnection | Only QA Evolution restarts; provider and app recover without re-pairing |
| Anti-loop and dedup | Outgoing echoes leave session intact; replay creates no duplicate |
| Temporary personal data | No phone/QR/secrets in Git or Jira; remove temporary pairing material |

Automated policy and route tests complement, but do not replace, real WhatsApp
acceptance. Do not check real transport cases until they are observed. Sending a
message from the paired account to itself does not prove inbound customer ingestion.

## Operations

1. Verify the eight tables and restrictive grants before enabling the pilot.
2. Deploy the reviewed branch preview with the configured environment.
3. Ensure the callback URL is reachable by Evolution, without a Vercel login page.
4. Create the instance through the app connection function, not an unrelated instance.
5. Present QR privately and immediately; refresh expired QR through the app.
6. Confirm the connected status in provider and database before sending.
7. Keep the assistant in test mode; use the existing transactional queue for fixed text.
8. Test a distinct sender, duplicate replay, outgoing echo and QA-only restart.
9. After merge, switch the QA callback to the canonical production endpoint and recheck it.
10. At the end of all QA tasks, disconnect the temporary number and remove QA personal
    data according to the retention policy. Do not delete unrelated store/customer data.

Evidence must distinguish automated, synthetic HTTP and real-device observations.
Local evidence belongs under a task-specific directory on D:, with sensitive pairing
material excluded from shared artifacts.
